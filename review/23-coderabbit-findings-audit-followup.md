# CodeRabbit findings audit — follow-up sweep (2026-07-04)

This is a follow-up to [review/19](19-coderabbit-findings-audit.md), which ran the repo's first
full-repo CodeRabbit sweep (2026-06-25) and fed a cleanup PR ([#483](https://github.com/BashfulBits/city-meeting-podcasts/pull/483))
plus several follow-up PRs. This sweep re-runs the same CLI procedure against current `main` five
weeks later, after ~130 more commits, to catch drift and cover code CodeRabbit hadn't scoped before
(`availability.py`, `availability_digest.py`, `check_endpoints.py`, `compare_timeline_diagnostics.py`,
and `scan_h16_log.py` all postdate the first sweep entirely).

**Relationship to [review/21](21-manual-code-audit-2026-07.md):** while this sweep was running,
a separate session independently produced review/21 — a manual line-by-line audit of the same six
directories, substituting for CodeRabbit CLI access that session didn't have. The two efforts overlap
in places (both, for example, separately found the CivicPlus/Swagit SSRF-adjacent gap and the
`contracts.py` presigned-URL truncation issue) and diverge in others (review/21's manual pass caught
a genuinely unguarded `ffprobe` call in `concat.py` this sweep's automated scan missed entirely;
this sweep caught structural bugs like the `RoutingStorage.put_cas` capability-check bypass and two
critical GitHub Actions bugs review/21 didn't examine as closely). Every overlapping finding below is
cross-linked both directions (`CR2-*` ↔ `MR-*`) rather than re-litigated — where the two verdicts
differ (the CivicPlus SSRF severity, most notably), this doc's row explains the reconciliation and
defers to whichever analysis was checked against the more current code.

**This sweep's original CodeRabbit run for `citypods/`/`scripts/`/`tests/` executed against commit
`54c9992`, which was current `main` at the time.** While it ran, `main` advanced to `f2ac1c7` via
three merged PRs (#800 media-size-ceiling guard, #801 review/21 itself, #802 a `pull_state` fix) that
touched several files this sweep already had findings for. Rather than re-running the CodeRabbit CLI
against the new tip (and re-spending rate-limit budget), every finding touching a file in that diff
was manually re-verified against current `main` by reading the actual diff; results are noted inline
where a finding was downgraded, corroborated, or superseded by newer code. `workers/`, `templates/`,
and `.github/` were scanned after this reconciliation, directly against current `main`, so those
three sections need no such caveat.

**This is a documentation/audit pass only** — no fixes were applied in this sweep (unlike review/19,
which fixed most findings directly via PR #483). Every "Confirmed valid — needs fix" row below is a
backlog item for a future fix PR.

Same procedure as review/19 (see [AGENTS.md § Running a full-codebase CodeRabbit review](../AGENTS.md)
for the mechanics): diff current `HEAD` against the repo's near-empty root commit so the whole tree
shows as one diff, one `coderabbit review --agent` run per top-level source directory. IDs in this
doc use the `CR2-` prefix (`CR2-CP-*`, `CR2-SC-*`, etc.) to keep this sweep's findings in their own
stable namespace, distinct from review/19's `CR-*` IDs and review/21's `MR-*` IDs. This sweep
cross-references every new finding against both prior docs' verdicts and:
- keeps a **compact "carried over" line** for an exact repeat of an already-"Confirmed no action"
  verdict (same file/line/pattern, reasoning still holds) rather than re-deriving the argument;
- flags a **regression** of a previously-"Fixed" item separately and prominently;
- **cross-links** (rather than duplicates) a finding independently confirmed by review/21;
- otherwise verifies each finding fresh against current code, exactly as review/19 and review/21 did.

**A note on false positives:** this run caught several CodeRabbit findings — including two rated
*critical* — that don't hold up against the actual code (see CR2-GH-02/CR2-GH-04/CR2-GH-20, and the
"Already fixed / invalid as framed" rows in `citypods/`). Automated severity labels in the raw
appendix are CodeRabbit's own and are **not** adjusted after verification; the Status/Rationale
columns are this audit's actual verdict.

## Summary

115 findings across 6 directories. **100 confirmed valid and not yet fixed** (backlog for a future
fix PR), **8 confirmed no action** (false positives or by-design, verified against actual code/
contracts), **4 carried over** from an already-"confirmed no action" verdict in review/19 or
review/21 with the reasoning re-checked and still holding, **2 already fixed / invalid as framed**
(CodeRabbit's premise didn't match current code), and **1 superseded** by a more current analysis in
review/21 after the underlying code changed mid-sweep. No regressions of any previously-fixed item
were found in any directory.

**Two findings are critical and still unmitigated**, both in `.github/workflows/`: **CR2-GH-06**
(`reset-backoff.yml` pipes a workflow input through an env var literally named `UID`, which bash's
own readonly `UID` builtin silently shadows — the manual recovery tool's `--uid` filter has never
actually worked) and **CR2-GH-07** (`clear-materialization.yml` splices `${{ inputs.run_id }}`
directly into shell script text rather than through `env:`, a script-injection shape with full
B2/R2/Cloudflare credentials in scope). Also worth flagging: **CR2-CP-47** (a real gap in the core
SSRF blocklist — RFC 6598's shared address space, 100.64.0.0/10, isn't blocked) and **CR2-CP-53**
(`RoutingStorage.put_cas` uses `hasattr` instead of the backend's own `cas_capable` flag, silently
degrading a CAS coordination write to non-atomic when R2 is absent). **CR2-CP-17** (the CivicPlus
SSRF gap) looked critical on first pass but was downgraded after reconciliation — see its row.

Three CodeRabbit findings rated **critical** by the tool were verified as **false positives**:
CR2-GH-02 and CR2-GH-20 both assumed the Granicus Worker's `npm test` needs a prior install step,
but its `package.json` declares zero dependencies (`node --test`, no lockfile); CR2-GH-04 assumed
`scan_h16_log.py` needs a missing-file guard, but the underlying function already degrades to zero
findings on a nonexistent path (verified live).
